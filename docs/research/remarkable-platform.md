# reMarkable 2 platform findings

Checked 2026-10-27 against reMarkable's developer portal, support site, and public source. These findings guide the first `7 × 8` prototype; the connected tablet now reports IMG_VERSION 3.28.0.172 and OS 5.8.203. Authenticated hardware findings and remaining physical checks are recorded in [the device checklist](../device-checklist.md).

## Verified

- reMarkable 2 runs reMarkable OS, a custom Linux distribution. Its product code is `rm2`. reMarkable publishes a product and OS version specific Yocto SDK containing a cross compiler, headers, and libraries. Match the tablet's **Settings → Software** version to the `rm2` row on the [official SDK links page](https://developer.remarkable.com/links); the number in `/etc/os-release` is not necessarily the number shown in Settings. [SDK guide](https://developer.remarkable.com/documentation/sdk)
- The SDK links page currently lists `rm2` SDKs through software 3.28.0.172 and, from 3.27.0.97 onward, both x86_64 and aarch64 Linux host installers. The SDK guide still says only x86_64 is published, so the [links page](https://developer.remarkable.com/links) is the more current inventory. Do not select or download an SDK until the tablet version is known.
- reMarkable's supported graphical example is **Qt 6 Quick**, not Qt Widgets. It uses `Qt6::Quick`, CMake, QML, `QGuiApplication`, and `QQmlApplicationEngine`. On device, the documented path stops `xochitl`, sets `QT_QPA_EVDEV_TOUCHSCREEN_PARAMETERS="rotate=180:invertx"` for reMarkable 2, then runs with `QT_QUICK_BACKEND=epaper` and `-platform epaper`. Restore `xochitl` after the session. [Qt Quick guide](https://developer.remarkable.com/documentation/qt_epaper), [official example code](https://github.com/reMarkable/remarkable-developer-examples)
- The official Qt guide says capacitive **touch** works out of the box, but handling the **Marker** is more involved and is not demonstrated. It does not establish that QML pointer handlers receive pen strokes or that a pen input plugin is publicly supported. That is the key hardware spike. [Qt Quick guide](https://developer.remarkable.com/documentation/qt_epaper)
- The official reMarkable 2 specifications list a 1872 × 1404 monochrome display and 4,096 pressure levels. The platform exposes an `epaper` Qt backend per the official guide. Its ink latency and partial refresh behavior for a custom app still require measurement. [reMarkable 2 specifications](https://support.remarkable.com/articles/Knowledge/About-reMarkable-2), [Qt Quick guide](https://developer.remarkable.com/documentation/qt_epaper)
- reMarkable 1 and 2 do **not** have a Developer Mode switch. The SDK guide demonstrates `scp` and `ssh root@10.11.99.1`; the Qt guide uses that connection to deploy and run. Developer Mode instructions on the portal apply to newer Paper Pro hardware. [SDK guide](https://developer.remarkable.com/documentation/sdk), [Developer Mode](https://developer.remarkable.com/documentation/developer-mode)
- `xochitl` is the proprietary main UI. reMarkable warns that compatibility across its versions is not guaranteed. A standalone prototype should use its own data in `/home/root` rather than rely on Xochitl document files or private APIs. [Xochitl guide](https://developer.remarkable.com/documentation/xochitl)

## To verify on the actual tablet

1. Record the software version from Settings and `cat /etc/os-release`; select the exact compatible `rm2` SDK. The official guide calls out a special `libqsgepaper.so` copy for 3.17, which should only be applied if that is the device version. [SDK links](https://developer.remarkable.com/links), [Qt Quick guide](https://developer.remarkable.com/documentation/qt_epaper)
2. Check SSH access and the device's input inventory (`/proc/bus/input/devices` and `/dev/input/by-path`). Do not hardcode an `eventN` path: the official Qt documentation does not specify one for Marker input. Identify the pen by device name/capabilities and measure axis ranges, orientation, pressure, contact, and eraser behavior.
3. Verify whether Qt Quick receives Marker events with the `epaper` platform. If it does not, read the Linux evdev pen device in a small native adapter, while keeping touch controls in Qt Quick. Confirm pen coordinates against the displayed writing area and capture actual point sequences before adding recognition.
4. Test full and partial redraw speed, ghosting, and pen latency on the device. Check app shutdown and reliable `xochitl` restart after interruption.
5. Check whether the selected SDK ships Qt SQL/SQLite, required runtime plugins, and a usable handwriting recognizer. The official materials above do not publish a third party Marker API or an embeddable handwriting recognition API. The product's MyScript powered handwriting conversion is a user feature, not evidence of an SDK usable by custom apps. [reMarkable 2 specifications](https://support.remarkable.com/articles/Knowledge/About-reMarkable-2)

## Deployment boundary

For the first prototype, build with the matched official SDK and run manually from `/home/root` over USB SSH. Do not modify boot services, the system UI, or Xochitl's document store. This follows the [official Qt deployment sequence](https://developer.remarkable.com/documentation/qt_epaper) and keeps the hardware experiment reversible.

## Refresh-mode finding from the connected tablet

On 2026-10-27, the installed rm2 3.28.0.172 E Ink backend's own Qt metadata and exported default-mode value revealed Content=4 as the default, with Mono=1 and Pen=0 available. Selecting Mono within this app improved perceived lag but retained the outline-then-fill effect. Selecting Pen produced explicit pen-update traces; the user confirmed the physical drawing/clearing/feedback test “looks perfect.” A fresh `56` was recognized correctly and persisted with 390 points. See the [full comparison and validation limits](../device-checklist.md#ink-refresh-investigation--2026-10-27).

The small adapter uses the installed library's private `EPScreenModeMap::uiScreenMode` export and `EPScreenModeItem::staticMetaObject`; it does not redistribute or modify the library. It is guarded to the exact verified rm2 firmware and falls back to backend defaults if compatibility checks fail. This is experimental compatibility code, not an official stable refresh API. Neither renderer submission timings nor visual confirmation establishes a numerical pen-to-screen latency or long-session ghosting guarantee.
